## 2. Бюджет целевых действий Авито

Текст правил прислал владелец; разбор и выводы для агента — в [avito-cpa-rules.md](avito-cpa-rules.md). Коротко: чат оплачивается один раз по первому признаку (контакт от любой стороны, адрес/часы работы, 5 реплик, ссылка, файл/фото, вопрос о предоплате); по оценке выгрузки около 40 из ~97 платных чатов стали платными из-за 5 реплик без телефона.

**Новое: фактические списания можно получить из API Авито**, раздел CPA:

- `POST /cpa/v2/chatsByTime` — список целевых (платных) чатов: ID чата (`channelId`), **сообщение, на котором сработало целевое действие** (`messageId`, `message`), тип контакта в нём (`contactType`: phone/email/nick/other), **тип целевого чата** (`targetChatType`: «Контакты / Сделка / Переключения»), цена в копейках, статус, можно ли опротестовать;
- `POST /cpa/v1/phonesInfoFromChats` — телефоны из целевых чатов с ценой;
- `POST /cpa/v2/callsByTime` — платные звонки: длительность, статус (целевой / на модерации / нецелевой), запись;
- `POST /cpa/v3/balanceInfo` — баланс.

Это журнал списаний с привязкой к чату и к сообщению-триггеру. По нему можно эмпирически увидеть, что именно делает чат платным в этом кабинете, сколько стоит, какие чаты оплачены без результата, и считать «расход на обращение» по факту, а не по догадкам. Текст правил всё равно нужен для политики агента (что можно, чего нельзя), но измерять расходы можно уже сейчас.

## 3. Первый этап: что делаем

Цель этапа: сравнивать стратегии A/B/C на одной модели воспроизводимо и считать конверсию правильно. Всё в тестовом режиме, без отправки клиентам и без живого A/B.

### 3.1. Версии агентов (стратегии отдельно от модели)

- Таблица `agent_versions`: ключ (`A_direct`), версия (`v0.1.0`), общая инструкция, текст стратегии, модель, temperature, статус (черновик / активна / архив). Использованную версию нельзя менять — правка создаёт новую.
- Промпт собирается из версии: общая инструкция 01 (адаптированная к JSON-ответу `reply/phone/handoff/skip`, клиент видит только `reply`) + стратегия + карточка авто + утверждённые факты.
- В `agent_runs` сохраняем: версию агента, модель и параметры, хэш промпта и сам текст промпта (таблица снимков по хэшу), версию базы знаний.
- Прогон запускает набор конфигураций «версия × модель» параллельно на одной точке диалога. Старые ответы не удаляются; сравнение группируется по конфигурации.
- Интерфейс: в «Проверке ответов» выбор конфигураций; таблица «конфигурация → доля 👍, нарушения, токены, время».

### 3.2. Воспроизводимая проверка

- Загрузить 20 проверочных ситуаций из `05_eval_cases.jsonl` в отдельную таблицу (не в базу знаний) + добавить многоходовые сценарии (вопрос → возражение → отказ от звонка / готовность дать номер).
- Автоматические проверки критичных нарушений для каждого ответа: цена, которой нет в карточке; «в наличии» при другой отметке; повторная просьба номера, когда он уже есть; повторное представление; заполнители в квадратных скобках; служебные метки в тексте; длина.
- Проверка по ожиданиям из `expected`: судья-модель (другая модель, чем у агента) ставит выполнено/нет по каждому пункту; результаты отдельно от оценки стиля.
- Слепая оценка человеком: ответы без названия варианта, в случайном порядке.
- Отчёт по конфигурациям: критичные нарушения (главное), доля выполненных ожиданий, слепые оценки.

### 3.3. Корректный учёт контакта и конверсии

- Один механизм распознавания телефона для импорта и живых сообщений: точки и другие разделители, склейка соседних сообщений клиента, ссылка на сообщения-источники, пометка неполных и неоднозначных номеров. Пересчитать по уже загруженной истории и сверить с 53 контактами Codex.
- Направление чата — по первому **человеческому** действию; системный сигнал (`flow_id`) хранится отдельно как тип события.
- Когортная конверсия: группа = чаты, где первое человеческое сообщение клиента попало в период; результат = новый телефон в окне 7 дней; незрелые группы показываются отдельно; телефон до первого ответа продавца/агента считается отдельно и не засчитывается ответу. Счётчик «контакты за день» оставить, но не называть конверсией.
- Проверка реализации: на той же выгрузке получить рабочую выборку и цифры, сопоставимые с Codex (206 входящих, 48 с телефоном, 23,3%), и объяснить расхождения.

### 3.4. База знаний: кандидаты и утверждённые факты

- У записей: статус (кандидат / утверждено / архив), источник, область (все / модель / конкретное авто), срок актуальности.
- В промпт как факты идут только утверждённые. Из разбора чатов и отчётов создаются кандидаты. Учебные примеры хранятся отдельно от фактов.
- Импорт v0.1.0 от Codex: инструкция 01 → общая инструкция версий; A/B/C → три версии; 22 примера → примеры (кандидаты); шаблон `06_live_facts` → форма «Факты компании» для заполнения. Имя в настройках — Ярослав.

### 3.5. Журнал списаний Авито (только чтение) и состояние чата

- Загрузка `chatsByTime`, `phonesInfoFromChats`, `callsByTime` в таблицу целевых действий с привязкой к чатам.
- Отчёт: сколько чатов оплачено, стоимость, тип целевого чата, на каком сообщении сработало, оплаченные чаты без телефона, возможность опротестовать.
- Состояние каждого чата по правилам п. 3.1: число реплик, сработавшие признаки, оплачен ли. Передавать агенту и показывать в чате; сверять оценку с фактическими списаниями.
- Кандидаты на опротестование в 7-дневный срок (звонок + чат одного покупателя, спам), только с подтверждением человеком.

Порядок внутри этапа: 3.3 и 3.5 (данные и метрики) → 3.1 → 3.4 → 3.2. Ориентировочно 2–3 рабочих сессии.
